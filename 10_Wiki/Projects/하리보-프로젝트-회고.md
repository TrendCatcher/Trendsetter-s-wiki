# 하리보 프로젝트 회고

## 핵심 — 에이전트의 해석

사용자 문제를 정의하는 일과, 그 의도를 팀원에게 전달하는 일은 함께 검토해야 한다. 이 회고는 기획 역량의 완성을 증명하는 사례가 아니라 자신의 관점도 수정한 기록이다.

## 직접 말한 사실 · 2026-07-12

근거: [하리보 프로젝트 복기](../../00_Raw/2026-07-12-%ED%95%98%EB%A6%AC%EB%B3%B4%20%ED%94%84%EB%A1%9C%EC%A0%9D%ED%8A%B8%20%EB%B3%B5%EA%B8%B0.md)의 주제선정·팀 회의·발표·느낀점·할일.

- 상사의 말을 귀여운 목소리로 바꾸는 아이디어로 팀 프로젝트를 시작했다.
- 기능을 나열하는 논의에 “우리가 해결하려는 문제와 페르소나는?”이라고 질문했다.
- 발표 피드백으로 대안재까지 분석한 점은 좋았지만, 설정한 페르소나와 후반 기능 전개가 맞지 않고 리텐션·수익화가 명확하지 않았다고 기록했다. 이는 사용자가 남긴 피드백 기록이다.

## 기대·마찰·관점 변화

| 단계 | 원본에서 남길 맥락 |
| --- | --- |
| 당시 기대 | 재미있는 아이디어로 시작해 사용자 상황을 탐색하며 방향을 정하고 싶었다 |
| 실제 마찰 | 팀이 기획 의도를 다르게 이해하고 기능 중심으로 논의한다고 느꼈다 |
| 망설임과 자기 수정 | “그럴 수 있다. 저 페르소나도 내 중심이기는 했다.” 팀원 평가에서 자신의 관점도 되짚는 방향으로 이동했다 |
| 다시 본 자신의 역할 | 자신의 의도를 구체적인 사용자 상황과 예시로 명확히 전달했어야 했다고 적었다 |
| 다음 시도 | 가용 시간·자원을 고려해 가설 검증 우선순위를 정하고 페르소나를 더 탐구하겠다고 적었다 |

## 에이전트의 해석

문제정의·페르소나·솔루션을 정리하라는 원칙만 추출하면 이 회고의 소통 문제와 자기 수정이 사라진다. 후속 기획에는 “내가 그린 사용자 상황을 다른 사람도 이해하는가”라는 질문까지 연결할 수 있다. 실제 후속 프로젝트에서 효과가 입증됐다는 뜻은 아니다.

## 현재 확인 필요

원본은 7/17까지 방향을 재검토할 계획을 적었다. 그 계획의 실행 여부, 후속 사용자 검증 결과와 현재 상태는 이 원본만으로 알 수 없다.

## 수정 이유 · 2026-09-10

이전의 “성공과 리텐션을 결정한다”는 일반화 대신 당시 경험과 해석을 구분했다. 실패·자기중심성 인식·전달 방식의 수정 맥락을 복원했다. 기존 0.85는 검증 확률이 아니므로 사용하지 않는다.
