# 디지털 헬스케어 데이터와 온톨로지 기반 서비스 기획

## 핵심 메시지

> 디지털 헬스케어에서 중요한 것은 단순히 많은 데이터를 확보하는 것이 아니라, **서로 다른 데이터를 식별하고 연결하여 실제 서비스에서 활용할 수 있도록 만드는 것**이다.

* 의료데이터는 이미 여러 곳에 존재하지만 서로 분리되어 있다.
* 환자 데이터, 의료기관 데이터, 문헌·연구 데이터가 연결되어야 의미 있는 서비스가 만들어진다.
* AI를 도입한다고 데이터 정제와 연결 문제가 자동으로 해결되지는 않는다.
* AI의 품질은 데이터의 양뿐만 아니라 **데이터의 표준화와 연결 품질**에 의해 결정된다.
* 공공데이터의 코드는 각 기관의 행정 목적에 맞게 설계되어 있으므로, 환자 중심 서비스를 만들 때 그대로 사용할 수 없는 경우가 있다.
* 서비스 기획자는 화면과 기능만 기획하는 사람이 아니라, **도메인의 데이터 구조와 식별 기준을 파악**하고 필요한 경우 **자체 온톨로지와 ERD까지 설계**해야 한다.

## 강의 정리

## 1. 디지털 헬스케어에서 데이터가 중요한 이유

디지털 헬스케어에서는 <span style= "color:red">**데이터**</span>가 중요하다.

하지만 데이터가 존재한다는 것과 데이터를 실제 의료서비스에 활용할 수 있다는 것은 다른 문제다.

예를 들어 환자가 애플워치의 수면 데이터를 의료진에게 보여주더라도, 의료진이 그 데이터를 바로 진료에 활용하기는 어렵다. 데이터를 의료진이 판단할 수 있는 형태로 번역하고, 다른 의료정보와 연결해 제공해야 하기 때문이다.

즉, 디지털 헬스케어에서 필요한 것은 단순한 데이터 수집이 아니라 다음 과정이다.

```text
데이터 수집
→ 데이터 식별
→ 표준화
→ 관계 정의
→ 의료적 맥락과 연결
→ 서비스에서 활용
```

## 2. 의료데이터 서비스의 예시

### 심평원·보험청구 기반 데이터

나의건강기록과 같은 PHR 서비스에서는 다음과 같은 정보를 확인할 수 있다.

* 복약 정보
* 처방·투약 기록
* 보험청구 과정에서 생성된 의료정보
* 외부 API를 통해 연결된 데이터

다만 보험청구를 위해 필요한 정보를 중심으로 데이터가 만들어졌기 때문에, 환자의 모든 건강정보를 포함하지는 않는다.

### 의료 마이데이터

의료 마이데이터에는 보험청구 정보뿐만 아니라 다음과 같은 정보가 포함될 수 있다.

* 신체정보
* 검사정보
* 진료기록
* 병원에서 생성된 여러 의료정보
* 개인이 직접 생성한 건강정보

의료 마이데이터의 주요 가치는 개인의 의료정보를 한곳에서 확인하고, 필요한 경우 다른 의료기관으로 전송할 수 있다는 점이다.

다만 서비스에서 확인되는 데이터가 사용자가 기억하는 자신의 의료기록과 항상 완전히 일치한다고 단정할 수는 없다. **각 기관이 데이터를 생성하는 목적과 기준이 다르기 때문이다.**

## 3. 데이터의 섬

의료데이터는 크게 세 영역으로 나누어 볼 수 있다.

1. **환자 데이터**

   * 환자가 일상생활에서 생성하는 데이터
   * 웨어러블 데이터
   * 운동·수면·식습관
   * 감정과 행동
   * 자가 측정 데이터

2. **의료기관 데이터**

   * 진료기록
   * 검사결과
   * 처방과 투약
   * 의료영상
   * 보험청구 데이터

3. **문헌·연구 데이터**

   * 임상연구
   * 논문
   * 진료지침
   * 의학적 근거
   * 약물과 치료법에 관한 연구결과

이 데이터들은 각각 존재하지만 서로 연결되지 않은 **데이터의 섬** 상태로 남아 있다.

디지털 헬스케어 서비스의 핵심 과제는 이 데이터들을 단순히 한곳에 모으는 것이 아니라, 서로 의미 있게 연결하는 것이다.

따라서 질환명 하나만으로 사용자를 분류해서는 개인화된 치료나 관리 서비스를 만들기 어렵다.

## 5. AI가 데이터 연결 문제를 모두 해결해 주는가

AI가 등장하면서 데이터 정제와 매핑 작업을 빠르게 할 수 있게 된 것은 사실이다.

하지만 데이터 정제 과정의 상당 부분은 여전히 사람이 직접 확인해야 한다. AI를 도입했다고 해서 기존에 100만큼 필요했던 작업이 곧바로 20으로 줄어드는 것은 아니다.

AI는 다음 작업을 도울 수 있다.

* 텍스트 유사도 분석
* 중복 데이터 탐지
* 형식 통일
* 후보 관계 추천
* 용어 매칭
* 이상 데이터 탐지

그러나 다음 사항은 여전히 사람이 판단해야 한다.

* 서로 다른 데이터가 실제로 같은 대상을 의미하는가
* 어떤 데이터를 기준값으로 사용할 것인가
* 예외 상황을 어떻게 처리할 것인가
* 의료적으로 잘못 연결될 위험은 없는가
* 서비스 목적에 맞는 데이터 구조인가

> **AI를 도입하는 것보다 데이터 연결 품질을 정의하는 것이 먼저다.**

## 6. Connection이 만드는 가치: 온톨로지를 활용한 표준화

### glossary
branch of philosophy that studies the **nature of reality, existence, and being**

온톨로지는 새로운 개념이라기보다 기존의 다음 개념들이 확장된 것으로 이해할 수 있다.

* 용어 표준화
* 마스터 데이터
* 분류체계
* 데이터 간 관계
* 지식 네트워크

### 온톨로지의 핵심 요소

#### 객체(Object)

현실 세계에 존재하는 엔티티다.

* 환자
* 질환
* 의약품
* 성분
* 검사
* 진단
* 의료기관
* 의료기기

#### 관계(Relationship)

객체들이 어떻게 연결되는지를 정의한다.

예시:

```text
환자 → 질환을 진단받는다
질환 → 특정 증상을 가진다
의약품 → 특정 성분을 포함한다
성분 → 특정 질환 치료에 사용된다
의약품 → 다른 의약품과 상호작용한다
검사 → 특정 진단의 근거가 된다
```

#### 액션(Action)

객체와 관계를 기반으로 실행하는 의사결정이나 운영 로직이다.

예시:

* 복약 가능 여부 판단
* 약물 상호작용 경고
* 진료 필요성 안내
* 적절한 관리 루틴 추천
* 특정 조건에서 의료진 상담 권고

### 도서관의 청구기호 비유

온톨로지는 도서관의 분류체계와 비슷하다.

도서관에 수많은 책이 있어도 분류체계와 청구기호가 없다면 원하는 책을 찾기 어렵다. 분류체계가 있기 때문에 책의 분야와 위치를 파악하고 정확한 자료를 찾을 수 있다.

AI도 마찬가지다.

온톨로지가 없다면 AI가 모든 원천 데이터를 직접 탐색하고 추론해야 한다. 이 과정에서 다음 문제가 발생할 수 있다.

* 불필요한 토큰 사용
* 같은 성분명을 서로 다른 표현으로 출력
* 약품명 혼동
* 상호작용 정보 누락
* 근거가 없는 답변 생성
* 할루시네이션 증가

## 7. 원스글로벌의 의약품 온톨로지 구성요소

원스글로벌은 의약품 데이터를 다음 관점에서 구조화했다.

* 성분명 표준화
* 한글·영문 성분명 연결
* 성분 간 관계 정의
* 성분 계층구조와 분류체계
* 성분과 적응증·질환 매핑
* 용량과 단위 표준화
* 투여 경로 구분
* 제형 구분
* 포장과 규격 구분
* 약물 상호작용 네트워크
* 부작용과 주의사항 연결

약은 약 자체로만 존재할 때보다 질환, 적응증, 용량, 투여 경로 및 상호작용과 연결될 때 데이터 가치가 높아진다.

예를 들어 다음 정보는 서로 구분되어야 한다.

```text
성분
→ 염 형태
→ 함량
→ 투여 경로
→ 제형
→ 용량 단위
→ 포장 규격
→ 제품
```

같은 성분이라도 함량, 제형, 투여 경로 및 포장 규격이 다르면 실제 서비스에서는 서로 다른 제품으로 다뤄야 할 수 있다.

## 8. 온톨로지 적용 여부에 따른 LLM 품질 차이

표준화되지 않은 식약처 원천 데이터를 그대로 학습한 모델은 동일한 성분명을 서로 다르게 표현할 수 있다.

예를 들어 같은 이부프로펜을 다음과 같이 출력할 수 있다.

* 이부프로펜
* Ibuprofen
* 일부는 영문, 일부는 한글로 된 혼합 표현
* 약칭이나 불완전한 성분명

이것은 모델 자체의 문제만이 아니라, 모델이 참조한 원천 데이터가 표준화되지 않았기 때문에 발생할 수 있다.

온톨로지가 있으면 다음 효과를 기대할 수 있다.

* **동일 성분을 같은 식별자로 인식**
* **서로 다른 표현을 표준명에 연결**
* 약물과 질환의 관계 추적
* 상호작용 탐색
* 근거 데이터 제시
* 검색 범위와 토큰 사용 감소
* 할루시네이션 가능성 감소

> **AI 품질은 데이터의 양만으로 결정되지 않는다. 데이터가 얼마나 정확히 식별되고 연결되어 있는지가 중요하다.**

## 9. 창업 시 필요한 공공데이터

의약품 서비스를 기획할 때 식품의약품안전처의 허가정보와 공공데이터는 중요한 출발점이 될 수 있다.

확인할 수 있는 정보에는 다음이 있다.

* 제품명
* 성분명
* 효능·효과
* 용법·용량
* 주의사항
* 품목기준코드
* 표준코드
* EDI 코드
* 포장과 규격

그러나 공공데이터를 가져오는 것만으로 서비스가 완성되는 것은 아니다.

공공데이터는 각 기관의 업무 목적에 맞게 만들어졌기 때문에, 환자 중심 서비스에서 필요한 식별 기준과 다를 수 있다.

## 10. 의약품 데이터의 PK 문제

데이터를 설계할 때 중요한 것은 각 데이터를 고유하게 식별할 수 있는 **PK(Primary Key)**다.

PK는 원칙적으로 다음 조건을 만족해야 한다.

1. 하나의 대상을 고유하게 식별해야 한다.
2. 값이 변하지 않아야 한다.
3. 대상과 코드가 가능한 한 1대1 관계여야 한다.
4. 중복되어서는 안 된다.

### 품목기준코드

처음에는 품목기준코드를 의약품의 PK로 사용할 수 있을 것처럼 보였다.

하지만 **같은 날짜에 여러 용량과 규격의 제품이 함께 허가되면 서로 다른 제품이 같은 품목기준코드를 가질 수 있다.**

예를 들어 다음 제품이 같은 품목기준코드로 묶일 수 있다.

```text
제품 A 5mL
제품 A 10mL
제품 A 15mL
```

환자 서비스에서는 5mL와 15mL가 서로 다른 제품으로 구분되어야 한다. 그러나 하나의 코드로 묶이면 특정 용량 정보가 누락되거나 잘못 표시될 위험이 있다.

따라서 품목기준코드는 서비스가 요구하는 1대1 PK로 사용하기 어렵다.

### 보험청구코드·EDI 코드

EDI 코드는 병원이나 약국이 **심평원(건강보험심사평가원)에 약값을 청구할 때 사용하는 코드**다.

그러나 다음과 같은 이유로 값이 변경될 수 있다.

* 급여·비급여 상태 변경
* 급여 삭제와 재등록
* 약가 조정
* 보험청구 기준 변경

행정기관 입장에서는 필요한 변경이지만, 불변해야 하는 서비스 내부 PK로 사용하기에는 적합하지 않다.

### 표준코드

표준코드는 제품의 규격과 포장 형태 등에 따라 대표코드와 일반코드가 구분될 수 있다.

예를 들어 같은 의약품이라도 다음 조건에 따라 코드가 달라질 수 있다.

* 병 포장
* PTP 포장
* 백 포장
* 규격
* 단위
* 제품 형태

따라서 서비스에서 정의한 하나의 제품 개념과 표준코드가 항상 단순한 1대1 관계를 형성하지 않는다.
=> 이해 더 필요..
### 결론

```text
품목기준코드
→ 여러 제품이 같은 코드를 가질 수 있음

EDI 코드
→ 급여와 약가 이력에 따라 변경될 수 있음

표준코드
→ 규격과 포장 기준에 따라 복수 코드가 존재할 수 있음
```

기존 코드를 그대로 PK로 사용하기 어렵다면 서비스 목적에 맞는 **자체 식별자**를 만들어야 한다.

---

## 11. 자체 PK와 매핑 구조 설계

원스글로벌은 제품과 성분을 서로 다른 개체로 정의하고 각각의 PK를 만들었다.

```text
성분 테이블
- 성분 PK
- 한글 성분명
- 영문 성분명
- 염 형태
- 성분 계열

제품 테이블
- 제품 PK
- 제품명
- 함량
- 제형
- 투여 경로
- 포장 규격
- 제조사

성분–제품 관계
- 하나의 제품에 어떤 성분이 포함되는지 연결
```

공공데이터에서 하나의 코드로 묶여 있는 여러 용량과 규격을 구분하기 위해 별도의 규격 데이터를 수집하고 통합했다.

```text
품목 데이터
+ 규격 데이터
+ 포장 데이터
→ 통합 데이터 생성
→ 실제 제품 단위로 분리
→ 자체 제품 코드 부여
```

제품 코드와 성분 코드를 각각 만든 뒤 두 테이블을 연결함으로써 다음과 같은 확장이 가능해진다.

* 제품과 성분 연결
* 성분과 질환 연결
* 제품과 부작용 연결
* 제품과 상호작용 연결
* 성분과 적응증 연결
* 제품별 용량과 투여 경로 관리

---

## 12. ERD와 데이터 백본

자체 PK가 정해지면 이를 기반으로 ERD를 설계할 수 있다.

ERD에서는 다음을 결정해야 한다.

* 핵심 엔티티는 무엇인가
* 각 테이블의 PK는 무엇인가
* 테이블을 연결하는 외래키는 무엇인가
* 관계가 1대1, 1대다, 다대다 중 무엇인가
* 어떤 속성을 별도 테이블로 분리할 것인가

초기에는 성분 DB와 제품 DB만으로 시작할 수 있다.

이후 서비스가 발전하면 다음 데이터를 연결한다.

```text
성분
↕
제품
↕
질환
↕
적응증
↕
부작용
↕
상호작용
↕
용법·용량
↕
환자 특성
```

처음부터 거대한 ERD를 만들 필요는 없다.

```text
성분과 제품부터 시작
→ 핵심 관계 검증
→ 질환 추가
→ 부작용 추가
→ 상호작용 추가
→ 환자 데이터와 연결
```

> 백엔드의 데이터 구조가 먼저 잡혀야 프론트엔드에서 어떤 정보를 어떤 방식으로 보여줄지를 설계할 수 있다.

---

## 13. 매핑 구조도가 만드는 차별점

매핑 구조도는 단순한 내부 문서가 아니다.

특정 도메인을 얼마나 깊이 이해하고 있는지 보여주는 핵심 자산이다.

의약품 분야라면 다음 항목의 관계를 그려야 한다.

* 성분명
* 제품명
* 함량
* 단위
* 투여 경로
* 제형
* 포장
* 규격
* 적응증
* 질환
* 부작용
* 상호작용

이 매핑 구조는 향후 다음 시스템의 기반이 된다.

* 데이터 백본
* 백오피스
* 검색 시스템
* 추천 시스템
* 의약품 비교 기능
* 상호작용 확인 기능
* AI 답변의 근거 구조

공공 API를 사용한다는 사실 자체는 차별점이 아니다.

공공데이터의 한계를 발견하고, 서로 다른 데이터를 어떤 기준으로 정제·분리·연결했는지가 실제 차별점이다.

---

## 14. 데이터 백본과 사용자 서비스의 차이

데이터를 연결하고 자체 식별자를 만드는 작업은 매우 어렵지만, 사용자에게는 그 과정이 직접 보이지 않는다.

투자자나 심사위원은 다음과 같이 질문할 수 있다.

> 공공 API를 가져오면 누구나 만들 수 있는 서비스 아닌가요?

이때 단순히 데이터 정제에 많은 시간이 들었다고 설명하는 것만으로는 서비스의 가치를 전달하기 어렵다.

데이터 백본은 서비스의 **기초 공사**다.

```text
데이터 식별·표준화
→ 데이터 연결
→ 정확한 검색과 판단
→ 사용자 기능
→ 사용자 가치
```

기초 공사를 한 뒤에는 이를 통해 사용자 경험이 어떻게 달라졌는지를 보여줘야 한다.

예를 들면 다음과 같다.

* 정확한 복약정보 제공
* 용량과 제품 혼동 방지
* 상호작용 누락 감소
* 환자에게 맞는 정보 제공
* 의료진과 환자 간 정보 전달 개선

---

## 15. 병원 중심에서 환자 중심으로의 변화

기존 의료서비스가 병원 안에서만 이루어질 때는 허가코드나 보험청구코드만으로도 충분한 경우가 있었다.

그러나 디지털 헬스케어는 병원 안의 행동을 환자의 일상으로 옮기고 있다.

```text
병원에서만 확인하던 정보
→ 환자가 집에서 확인

의료진이 관리하던 행동
→ 환자가 스스로 관리

기관 중심 데이터
→ 환자 중심 데이터
```

환자가 집에서 자신의 약과 건강정보를 직접 확인하려면 행정기관의 코드보다 더 세밀하고 정확한 데이터 구조가 필요하다.

## 16. 정신질환 분야의 온톨로지는 어떻게 시작할 것인가

먼저 만들고자 하는 서비스의 범위를 구분해야 한다.

```text
심리상담 서비스인가?
정신질환 치료를 지원하는 서비스인가?
생활관리와 웰니스 서비스인가?
의료진의 진단과 치료를 보조하는 서비스인가?
```

치료 영역을 대상으로 한다면 다음 순서로 구조를 그릴 수 있다.

### 1. 질환 구분

* 우울증
* 조현병
* 양극성장애
* 불안장애
* 공황장애
* 외상후스트레스장애

### 2. 세부 질환과 상태 구분

* 급성·만성
* 중증도
* 재발 여부
* 동반질환
* 특정 증상
* 위험요인

### 3. 진단 기준과 평가방법

* 진단 기준
* 진단 기법
* 평가척도
* 증상
* 중증도
* 기능 저하

### 4. 치료방법

* 약물치료
* 심리치료
* 인지행동치료
* 디지털 치료기기
* 생활습관 관리
* 의료진 상담

### 5. 관계 매핑

```text
질환 → 증상을 가진다
평가척도 → 증상의 정도를 측정한다
진단 기준 → 질환을 구분한다
치료법 → 특정 질환에 적용된다
약물 → 특정 성분을 포함한다
약물 → 부작용을 가질 수 있다
생활데이터 → 증상 변화와 관련될 수 있다
```

처음부터 모든 정신질환을 대상으로 할 필요는 없다.

전체 지도를 대략적으로 그린 다음, 우울증과 같이 하나의 질환을 선택해 깊게 파고드는 방식이 적합하다.

> 질환을 분류하고, 진단 기준과 치료방법을 연결해 지도를 만드는 것 자체가 온톨로지 구축의 시작이다.

## 17. 도메인 공부를 어디서 시작해야 하는가

서비스 기획자는 의료진이 아니기 때문에 자신이 만든 분류가 의학적으로 정확한지 확인하기 어렵다.

따라서 다음 순서가 적절하다.

1. 국내 학회와 공공기관의 가이드라인 확인
2. 교과서적 분류와 진단 기준 파악
3. 질환·증상·진단·치료 관계도 작성
4. 서비스에서 필요한 범위 결정
5. 의료진과 전문가에게 자문
6. 사용자 인터뷰
7. MVP에서 필요한 데이터만 선택

논문이나 특정 저자의 주장을 깊이 파고드는 것은 연구에는 도움이 될 수 있지만, 서비스 기획을 시작하는 단계에서는 논쟁적인 주장에 빠져 전체 구조를 잡지 못할 위험이 있다.

우선 보편적으로 인정된 기준으로 기본 지도를 만든 뒤, 새로운 관점과 연구를 추가하는 편이 좋다.

---

## 18. 서비스 기획자의 역할

도메인 지도를 만들고, 기준을 정하고, 데이터 구조를 설계하는 일은 대표나 개발자만의 일이 아니다.

특히 초기 스타트업에서는 서비스 기획자가 다음 역할을 맡을 수 있다.

* 도메인 조사
* 데이터 출처 조사
* 코드 체계 분석
* 예외 사례 탐색
* 자체 식별 기준 정의
* 온톨로지 설계
* ERD 초안 작성
* 의료진 및 전문가 자문
* 고객 인터뷰
* 기능 요구사항 설계
* 화면과 데이터의 연결 정의

준비가 완료된 대기업의 후속 업무가 아니라, 처음부터 서비스를 만드는 조직에 들어간다면 이러한 기반 작업을 직접 해야 할 가능성이 높다.

## 19. 경쟁사 분석과 MVP 설계

서비스를 만들 때는 글로벌 경쟁사와 국내 경쟁사를 함께 살펴본다.

### 경쟁사 분석에서 확인할 항목

* 주요 고객
* 해결하는 문제
* 핵심 기능
* 수익구조
* B2C·B2B 여부
* 계약 방식과 가격
* 사용 데이터
* 데이터 수집 방식
* 의료기관과의 협업 방식
* 업데이트 내역
* 사용자 리뷰
* 경쟁사 간 공통 기능

여러 경쟁사가 공통으로 제공하는 기능은 해당 시장에서 사용자가 기본적으로 기대하는 기능일 가능성이 높다.

```text
경쟁사 공통 기능
→ 시장의 기본 기대치

경쟁사마다 다른 기능
→ 포지셔닝과 차별점 후보

아직 해결되지 않은 불편
→ 새로운 서비스 기회
```

경쟁사를 모두 분석하더라도 하나의 정답이 나오는 것은 아니다. 경쟁사 분석의 목적은 기능을 그대로 복제하는 것이 아니라 시장의 기준점과 빈틈을 파악하는 것이다.

### MVP 설계 순서

1. 경쟁사 분석을 통해 시장의 기본 기능을 파악한다.
2. 사용자 인터뷰로 실제 문제가 존재하는지 확인한다.
3. 문제 해결에 필요한 최소 기능을 묶는다.
4. 필요한 데이터를 정의한다.
5. DB 백본과 핵심 엔티티를 설계한다.
6. 프로토타입을 만든다.
7. 사용자의 반응을 확인한다.
8. 기능과 타깃을 계속 수정한다.

## 20. 타깃 고객을 설정할 때의 주의점

타깃을 지나치게 넓게 잡으면 문제와 해결책이 추상적으로 보일 수 있다.

반대로 지나치게 좁게 잡으면 시장 규모와 수익성이 부족할 수 있다.

타깃은 단순히 연령이나 성별만으로 정하지 않고 다음을 함께 고려해야 한다.

* 해결하려는 문제
* 질환 단계
* 행동 특성
* 관리 필요성
* 서비스 사용 상황
* 지불 의사
* 기존 대안
* 서비스가 필요한 빈도

예를 들어 당뇨 관련 서비스라면 다음처럼 나눌 수 있다.

```text
현재 당뇨 질환자
당뇨 전단계 사용자
가족력으로 위험을 느끼는 사용자
생활습관 개선이 필요한 사용자
건강검진에서 경고를 받은 사용자
```

한 서비스 안에서도 사용자 상태에 따라 다른 기능을 제공하는 방식으로 시장을 확장할 수 있다.

초기 페르소나와 실제 사용자가 다를 수도 있다. 강사의 서비스 역시 처음에는 아이를 키우는 부모나 약을 많이 복용하는 중장년층을 예상했지만, 실제 주요 사용자는 20~30대였다.

따라서 페르소나는 고정된 정답이 아니라 검증하고 수정해야 하는 가설이다.

---

## 21. 고객의 Pain Point

고객의 Pain Point를 정확히 파악하고 공감을 얻는 것은 중요하다.

하지만 기획자의 머릿속에 있는 문제와 고객이 실제로 느끼는 문제는 다를 수 있다.

다음 과정을 반복해야 한다.

```text
가설 설정
→ 고객을 직접 만남
→ 행동과 데이터 관찰
→ 프로토타입 제작
→ 반응 확인
→ 가설 수정
```

완벽한 아이디어를 머릿속에서 오래 고민하는 것보다 작은 프로토타입이나 기획서를 계속 만들어 보는 것이 중요하다.

성공하거나 실패한 결과물이 축적되면 다음 판단이 가능해진다.

* 타깃을 변경할 것인가
* 질환군을 변경할 것인가
* 기능을 줄일 것인가
* 다른 기업과 데이터를 연동할 것인가
* 사업 모델을 수정할 것인가

---

## 22. 웹페이지 상세 목차 구축

현재 고객 인터뷰가 진행 중이라면 다음 순서로 웹페이지와 서비스를 구체화할 수 있다.

1. 글로벌·국내 경쟁사를 분석한다.
2. 경쟁사가 공통으로 제공하는 기능을 파악한다.
3. 고객 인터뷰를 통해 기능의 필요성을 검증한다.
4. 최소 기능을 묶어 MVP 범위를 결정한다.
5. 화면에 필요한 데이터를 정의한다.
6. DB 백본과 매핑 구조를 설계한다.
7. 핵심 사용자 흐름을 만든다.
8. 프로토타입을 제작하고 검증한다.

## 23. 데이터 렌더링 시 주의사항

화면에서 데이터를 어떻게 보여줄지는 데이터의 목적과 사용자의 행동에 따라 달라진다.

### 카드 형태가 적합한 경우

* 핵심 정보 몇 개를 빠르게 보여줄 때
* 모바일 화면에서 확인할 때
* 사용자별 요약정보를 보여줄 때
* 행동을 유도해야 할 때
* 우선순위가 명확할 때

### 표 형태가 적합한 경우

* 여러 항목을 비교할 때
* 수치와 속성이 많을 때
* 전문가나 관리자용 화면일 때
* 정렬과 필터가 필요할 때
* 데이터의 전체 구조를 확인해야 할 때

첫 화면에서는 사용자가 가장 먼저 알아야 하는 정보를 우선 배치해야 한다.

화면 설계에서도 다음을 함께 고려한다.

* 경쟁사는 어떤 정보를 우선 보여주는가
* 핵심 고객은 모바일과 PC 중 무엇을 사용하는가
* 사용자가 첫 화면에서 내려야 하는 판단은 무엇인가
* 어떤 정보가 행동으로 연결되는가
* 어떤 정보가 지나치게 전문적이거나 복잡한가

## 나의 통찰

의료데이터를 파악하고 온톨로지를 구축하는 것은 결국 서비스를 만드는 우리의 몫이다.

공공데이터나 기존 의료데이터를 가져오는 것만으로는 차별점이 되지 않는다. 데이터를 어떤 기준으로 분류하고 연결할지 결정하는 과정이 서비스의 핵심 자산이 된다.

정신질환 상담기록, 복용약, 진단, 신체데이터를 확보한다고 하더라도 이 데이터들을 어떤 구조로 연결할 것인지 고민해야 한다.

현재 내가 파악해야 할 것은 다음과 같다.

```text
정신질환
→ 질환별 분류
→ 증상
→ 진단 기준
→ 평가도구
→ 중증도
→ 치료방법
→ 복용약
→ 신체·생활 데이터
→ 치료 결과
```

현재 『브레인 에너지』를 읽고 있지만, 한 저자의 주장이나 논쟁적인 치료 이론부터 깊게 파고들기보다 국내에서 실제로 사용하는 진단 기준과 가이드라인을 먼저 파악하는 것이 좋다.

1. 전체 정신질환의 큰 지도를 그린다.
2. 상담·웰니스·치료 중 서비스 영역을 결정한다.
3. 우울증과 같이 하나의 질환부터 선택한다.
4. 진단 기준과 평가기법을 정리한다.
5. 치료법과 약물을 연결한다.
6. 생활·신체데이터와의 관계를 탐색한다.
7. 의료진에게 구조의 적절성을 검증받는다.
8. 실제 사용자의 Pain Point를 인터뷰한다.

기획자는 완성된 데이터를 받아 화면만 만드는 사람이 아니다.

> 어떤 데이터가 필요하고, 무엇을 하나의 객체로 정의하며, 어떤 관계로 연결할지를 결정하는 것 역시 기획이다.

---

## 전사 기반 통찰 확장

### 1. 온톨로지 구축의 출발점은 데이터가 아니라 서비스 범위다

정신질환 데이터를 무작정 모두 모으기 전에 내가 만들려는 서비스가 무엇인지 먼저 결정해야 한다.

* 상담 서비스
* 자가관리 서비스
* 정신질환 치료 보조
* 복약관리
* 재발 모니터링
* 의료진용 의사결정 지원

서비스의 목적에 따라 필요한 객체와 관계가 달라진다.

### 2. 정신질환 온톨로지의 초기 객체 후보

```text
질환
증상
진단 기준
평가척도
중증도
치료법
약물
성분
부작용
생활습관
신체지표
의료기관
상담기록
사용자 행동
임상 가이드라인
```

### 3. 초기 관계 후보

```text
질환은 증상을 가진다
평가척도는 증상의 정도를 측정한다
진단 기준은 질환을 구분한다
치료법은 질환에 적용된다
약물은 성분을 포함한다
약물은 부작용을 가질 수 있다
생활습관은 증상 변화와 관련될 수 있다
신체지표는 위험 신호가 될 수 있다
가이드라인은 진단과 치료의 근거가 된다
```

이 구조는 완성된 정답이 아니라 의료진과 사용자를 만나면서 계속 수정해야 하는 가설이다.

## 아이디어 발전 방향

### 아이디어 1. 정신건강 도메인 맵 구축 도구

정신질환의 질환·증상·진단·치료·약물·생활데이터를 시각적으로 연결하는 도구다.

#### 대상

* 디지털 헬스케어 기획자
* 초기 정신건강 스타트업
* 의료서비스 연구자
* 비의료인 창업자

#### 주요 기능

* 질환별 맵
* 진단 기준 연결
* 평가척도 연결
* 약물과 치료법 연결
* 출처와 가이드라인 표시
* 의료진 검수 상태 표시
* 서비스별 필요한 데이터 선택

### 아이디어 2. 정신건강 서비스용 데이터 백본

사용자의 다음 데이터를 하나의 구조로 연결한다.

* 자가 기록
* 감정일기
* 수면
* 활동량
* 복용약
* 상담기록
* 평가척도
* 신체증상
* 스트레스 사건

단, 이 데이터를 곧바로 질환 진단으로 연결해서는 안 된다. 웰니스 정보, 위험 신호, 의료적 진단을 명확히 구분해야 한다.

### 아이디어 3. 강의 필기에서 데이터 구조를 추출하는 AI Agent

현재 진행 중인 Hermes Agent와 연결할 수 있다.

```text
강의 필기
+ 음성 전사본
→ 핵심 개념 추출
→ 객체 후보 추출
→ 관계 후보 추출
→ 도메인 맵 생성
→ ERD 후보 생성
→ MVP 기능 후보 생성
```

AI가 자동 생성한 관계는 바로 확정하지 않고 다음 상태로 관리한다.

```text
AI 제안
→ 사용자 검수
→ 전문가 검수
→ 승인된 관계만 온톨로지에 반영
```

이 과정을 반복하면 강의 복습 자료가 단순한 필기에서 끝나지 않고, 실제 제품 개발에 활용할 수 있는 도메인 지식과 데이터 자산으로 축적될 수 있다.
